Benchmark Configuration:
  - Number of seeds (N):       30
  - Seed range:                42 to 71 (inclusive)
  - Simulation steps per run:  1000 (1 step = 1 second of simulated time)
  - Control modes:             3 (Fixed, Density-Adaptive, Proximity-RL)
  - Security configurations:   2 (Without Security, With RSA/AES Security)
  - Total simulation runs:     3 × 30 × 2 = 180

Seed Usage:
  Each seed value s ∈ {42, 43, ..., 71} is passed to:
    - Python:  random.seed(s) and numpy.random.seed(s)
    - SUMO:    --seed s (controls vehicle departure times, route choices)
  This ensures full reproducibility of each individual run.

Control Modes:
  1. Fixed:      Constant 30-second green phase per direction
  2. Density:    Adaptive green time (10–45s) based on real-time lane density
  3. Proximity:  Hybrid DQN RL that activates within 250m of emergency vehicles,
                 falls back to density-based control elsewhere

Security Configuration:
  - Without Security: No encryption or authentication overhead
  - With Security:    RSA-4096 Certificate Authority, RSA-2048 per entity,
                      AES-256-GCM symmetric encryption for V2V/V2I messages

Network Parameters:
  - V2V Protocol:    IEEE 802.11p (WiFi), range = 300m
  - V2I Protocol:    WiMAX (emergency vehicles), range = 1000m
                     WiFi 802.11p (regular vehicles), range = 300m
  - Beacon interval: 0.1s (10 Hz)
  - RSUs:            13 at intersection/road-segment positions


================================================================================
  2. NOTATION & AGGREGATION — WHAT "±" MEANS
================================================================================

For each metric M, we collect one scalar value per simulation run.
For a given mode and security setting, we have N = 30 values:

    M_1, M_2, ..., M_N     (one per seed)

The table reports:  mean ± std

  Mean (arithmetic average):

                        1   N
              μ_M  =  --- Σ  M_i
                       N  i=1

  Standard Deviation (population, not sample):

                          ┌         ┐ 1/2
                          │ 1   N   │
              σ_M  =      │--- Σ (M_i - μ_M)²│
                          │ N  i=1  │
                          └         ┘

  NOTE: We use numpy.std() which computes the POPULATION standard deviation
  (ddof=0 by default), dividing by N (not N-1).

  Reported as:  μ_M ± σ_M

  Example: "16.50 ± 0.42" means the mean across 30 seeds is 16.50 and
  the population standard deviation is 0.42.

  Code reference (run_benchmark.py, aggregate_metrics function):
    agg[key] = {
        'mean': np.mean(values),    # μ = (1/N) Σ M_i
        'std':  np.std(values),     # σ = sqrt((1/N) Σ (M_i - μ)²)
        'min':  np.min(values),
        'max':  np.max(values),
        'n':    len(values),        # = 30
    }


================================================================================
  3. PER-RUN METRIC DEFINITIONS
================================================================================

Each of the 180 simulation runs produces the following metrics. These are
the raw per-run values that then get aggregated across seeds as described
in Section 2.

Source file: sumo_simulation/run_complete_integrated.py


--- 3.1  AVERAGE WAIT TIME (seconds) ---

  Definition: Mean total waiting time across all vehicles that completed
  their trip during the simulation.

  A vehicle is considered "waiting" when its instantaneous speed < 0.1 m/s
  (effectively stopped at a red light or in congestion).

  For each vehicle v that completes its trip (arrives at destination):

    W_v = Σ_{t ∈ trip(v)} 1_{speed_v(t) < 0.1}

  Where:
    - trip(v) is the set of simulation steps where vehicle v exists
    - speed_v(t) is the instantaneous speed (m/s) from traci.vehicle.getSpeed()
    - 1_{...} is the indicator function (= 1 if condition true, else 0)
    - Each step = 1 second, so W_v is in seconds

  Per-run metric:
                         1
    avg_wait_time  =  ------- Σ  W_v
                       |C|   v∈C

  Where C is the set of completed vehicles (reached their destination).


--- 3.2  AVERAGE TRIP SPEED (m/s) ---

  Definition: Mean average speed across all completed vehicles.

  For each completed vehicle v:

    D_v = Σ_{t ∈ trip(v)} speed_v(t)      (total accumulated distance, meters)
    T_v = |trip(v)|                         (trip duration in steps/seconds)
    S_v = D_v / max(T_v, 1)               (average speed over trip)

  Note: D_v = Σ speed_v(t) × Δt where Δt = 1s, so D_v ≈ total distance.

  Per-run metric:
                          1
    avg_trip_speed  =  ------- Σ  S_v
                        |C|   v∈C


--- 3.3  AVERAGE QUEUE LENGTH (vehicles) ---

  Definition: Mean total halting vehicles across all junctions, averaged
  over all simulation steps.

  At each step t:

    Q(t) = Σ_{j ∈ J} Σ_{l ∈ lanes(j)} halting(l, t)

  Where:
    - J is the set of all traffic-light-controlled junctions
    - lanes(j) are the controlled lanes of junction j
    - halting(l, t) = traci.lane.getLastStepHaltingNumber(lane)
      (SUMO definition: vehicles with speed < 0.1 m/s on that lane)

  Per-run metric:
                             1
    avg_queue_length  =  ------- Σ  Q(t)
                          |T|   t∈T

  Where T is the set of simulation steps where vehicles were present
  (metric_steps counter).


--- 3.4  TOTAL COMPLETED VEHICLES (count) ---

  Definition: Number of vehicles that reached their destination during
  the simulation.

    total_completed_vehicles = |C|

  A vehicle is "completed" when it disappears from the SUMO vehicle list
  between consecutive steps (previous_vehicles - current_vehicles), meaning
  it arrived at its route destination.


--- 3.5  THROUGHPUT (vehicles per minute) ---

  Definition: Rate of vehicle completions normalized to wall-clock time.

    throughput = |C| / max(elapsed_time_minutes, 1)

  Where elapsed_time_minutes = (wall-clock end - wall-clock start) / 60.

  NOTE: This is wall-clock throughput, not simulated-time throughput.
  This is why throughput differs between security/no-security (security
  adds ~2× wall-clock time due to RSA key generation), even though the
  same number of vehicles complete their trips.


--- 3.6  EMERGENCY AVERAGE WAIT TIME (seconds) ---

  Same formula as 3.1, restricted to emergency vehicles:

                             1
    emergency_avg_wait = -------- Σ  W_v
                          |C_e|  v∈C_e

  Where C_e = {v ∈ C : "emergency" ∈ vehicle_id(v)}

  Emergency vehicles are identified by the substring "emergency" in their
  SUMO vehicle ID.


--- 3.7  EMERGENCY AVERAGE SPEED (m/s) ---

  Same formula as 3.2, restricted to emergency vehicles:

                              1
    emergency_avg_speed = -------- Σ  S_v
                           |C_e|  v∈C_e


--- 3.8  EMERGENCY VEHICLES COMPLETED (count) ---

    emergency_completed = |C_e|


--- 3.9  NORMAL AVERAGE WAIT TIME (seconds) ---

  Same formula as 3.1, restricted to non-emergency vehicles:

                           1
    normal_avg_wait = -------- Σ  W_v
                       |C_n|  v∈C_n

  Where C_n = C \ C_e  (all completed vehicles excluding emergency)


--- 3.10  NORMAL AVERAGE SPEED (m/s) ---

                            1
    normal_avg_speed = -------- Σ  S_v
                        |C_n|  v∈C_n


--- 3.11  NORMAL VEHICLES COMPLETED (count) ---

    normal_completed = |C_n|


--- 3.12  WiFi PACKET DELIVERY RATIO — PDR (%) ---

  Definition: Percentage of WiFi (802.11p) packets successfully received
  out of all packets transmitted, across both V2V and V2I communication.

                       wifi_packets_received
    wifi_pdr (%) = ─────────────────────────── × 100
                        wifi_packets_sent

  WiFi is used for:
    - V2V: All vehicle-to-vehicle communication (beacon messages)
    - V2I: Regular (non-emergency) vehicle to RSU communication

  The per-packet success probability depends on distance d:

    P_success(d) = max(0.92, 1.0 - (d / R_wifi) × 0.08)

  Where R_wifi = 300m (WiFi range).

  This models a minimum PDR of 92% at maximum range, linearly decreasing
  from 100% at d=0 to 92% at d=300m.

  Packet delivery is determined deterministically using a hash function:

    delivered = (hash(source_id, dest_id, timestamp) mod 100) / 100 < P_success(d)


--- 3.13  WiMAX PACKET DELIVERY RATIO — PDR (%) ---

  Definition: Percentage of WiMAX packets successfully received out of all
  WiMAX packets transmitted (V2I communication for emergency vehicles only).

                        wimax_packets_received
    wimax_pdr (%) = ──────────────────────────── × 100
                         wimax_packets_sent

  WiMAX is used exclusively for emergency vehicle to RSU communication.

  Per-packet success probability:

    P_success(d) = max(0.95, 1.0 - (d / R_wimax) × 0.05)

  Where R_wimax = 1000m (WiMAX range).

  This models a minimum PDR of 95% at maximum range, linearly decreasing
  from 100% at d=0 to 95% at d=1000m.


--- 3.14  SIMULATION TIME (seconds) ---

  Wall-clock elapsed time for the simulation run:

    elapsed_time_s = wall_clock_end - wall_clock_start

  Measured using Python's time.time(). Includes all computation:
  traffic control, network simulation, security operations (if enabled).

================================================================================
  7. KEY OBSERVATIONS FOR PAPER
================================================================================

1. Traffic metrics (wait time, speed, queue length, completed vehicles) are
   IDENTICAL between security and no-security configurations. This is because:
   - Security operates at the application layer (RSA/AES encryption)
   - SUMO's traffic simulation is fully deterministic for a given seed
   - Security does not affect traffic light phase decisions

2. The only metrics that differ between security/no-security are:
   - Throughput (veh/min): Lower with security due to ~2× wall-clock time
   - Simulation Time (s): ~2× longer with security (RSA key generation)
   - WiFi/WiMAX PDR: Marginal differences due to timing of network events

3. Standard deviation is POPULATION std (divides by N), not SAMPLE std
   (which divides by N-1). For N=30, the difference is minimal:
   σ_sample = σ_population × sqrt(N/(N-1)) = σ_population × 1.017

4. All 30 seeds produce complete results (30/30) for every mode/security
   combination. No runs failed or were excluded.

--- 10.1  FIXED MODE ---

  Green duration = fixed_green_time = 30 seconds (constant, no adaptation).
  All green phases last exactly 30 s regardless of traffic conditions.
  Yellow phase = 3 s.
  Full cycle = 2 × (30 + 3) = 66 seconds per intersection.


--- 10.2  DENSITY-ADAPTIVE MODE ---

  Green duration is computed per junction per phase based on real-time
  lane density using traci.lane.getLastStepVehicleNumber() and
  traci.lane.getLastStepHaltingNumber().

  Lane density formula:

    For each green lane i in current phase:
      weighted_count_i = vehicles_i + halting_i × 0.5

    density = (Σ weighted_count_i) / max(green_lane_count, 1)

  Green time mapping (piecewise linear):

    If density >= 10:        target_duration = 45 s  (max_green)
    If density <= 3:         target_duration = 10 s  (min_green)
    Otherwise:
      scale = (density - 3) / (10 - 3)
      target_duration = floor(10 + scale × (45 - 10))
                      = floor(10 + scale × 35) seconds

  When time_in_phase >= target_duration, transition to yellow.


--- 10.3  EMERGENCY VEHICLE PRIORITY (all modes) ---

  Detection: Every step, the controller checks all vehicles. If a vehicle
  has "emergency" in its type name and is within emergency_detection_range
  (150 m) of a traffic light junction, it is given priority.

  Priority action: The traffic light immediately switches to the phase
  that gives green to the emergency vehicle's approach direction. If
  already in the correct phase, the green timer is extended by resetting
  time_in_phase to max(0, time_in_phase - 5), effectively adding 5 s.

  First-come-first-served: If multiple emergency vehicles approach,
  priority goes to the first detected. Served emergency vehicles are
  tracked to avoid re-triggering.

  11. PROXIMITY-RL HYBRID (DQN) CONFIGURATION
================================================================================

--- 11.1  HYBRID CONTROL LOGIC ---

  Source: sumo_simulation/run_complete_integrated.py (ProximityHybridController)

  The proximity-RL mode operates as a hybrid:
    - Within 250 m of any emergency vehicle: DQN RL agent takes control
    - Outside 250 m of all emergency vehicles: Density-adaptive control

  Proximity threshold: 250.0 m (passed via --proximity 250)

  At each simulation step:
    1. Check all vehicles with "emergency" in their type name
    2. Calculate Euclidean distance from each traffic light (J2, J3) to
       the nearest emergency vehicle
    3. If min_distance ≤ 250 m → RL agent selects the traffic light action
    4. If min_distance > 250 m → Density-adaptive mode (Section 10.2)


--- 11.2  DQN MODEL HYPERPARAMETERS ---

  Trained model: rl_module/trained_models/dqn_traffic_20260304_222100/
  File: dqn_traffic_final.zip  (stable-baselines3 format)

  ├─────────────────────────┼───────────────────────────────────────────┤
  │ Algorithm               │ DQN (Deep Q-Network)                     │
  │ Framework               │ stable-baselines3 (v2.3.2)               │
  │ Policy                  │ MlpPolicy (Multi-Layer Perceptron)       │

    - Traffic light constraint: min = 5 s, max = 60 s
    - β (reward scaling): 20


--- 11.3  REWARD FUNCTION ---

  The DQN reward is a weighted combination:

    R_total = { 0.3 × R_base + R_emergency + 0.5 × R_queue,  if emergency present
              { R_base + R_queue,                               otherwise

  Components:

  1. Speed reward (α₁ = 0.01):
     +0.01 per vehicle with speed > 8 km/h threshold

  2. Waiting penalty (α₂ = -0.5):
     -0.5 per idle vehicle (waited > 60 steps)
     Additional penalty of -50 for max-wait violations

  3. Emergency reward (α₃):
     +200 for fast emergency vehicle passage
     +100 for moderate emergency vehicle speed
     -150 for slow emergency vehicles
     -100 for excessive emergency vehicle wait
     +50  green-wave bonus (emergency gets consecutive greens)

  4. Queue penalty (α₄):
     -20 per lane with severe congestion (avg speed < 2 m/s)
     -5  per lane with moderate congestion (avg speed < 5 m/s)

================================================================================
  13. COMMUNICATION NETWORK PARAMETERS
================================================================================

Source: sumo_simulation/sumo_ns3_bridge.py (SUMONS3Bridge)


--- 13.1  IEEE 802.11p (WiFi) — V2V & V2I (regular vehicles) ---

  Maximum range:   300 m
  Beacon interval: 0.1 s (10 Hz)
  Base delay:      20 ms + (d / 300) × 30 ms

  Packet Delivery Ratio (PDR) model:

    P_wifi(d) = max(0.92, 1.0 − (d / 300) × 0.08)

    At d = 0 m:    P = 1.00 (100%)
    At d = 150 m:  P = 0.96 (96%)
    At d = 300 m:  P = 0.92 (92%)

  Used for:
    - V2V: All vehicle-to-vehicle beacon messages
    - V2I: Regular (non-emergency) vehicle ↔ RSU communication


--- 13.2  WiMAX — V2I (emergency vehicles only) ---

  Maximum range:   1000 m
  Base delay:      15 ms + (d / 1000) × 15 ms

  Packet Delivery Ratio (PDR) model:

    P_wimax(d) = max(0.95, 1.0 − (d / 1000) × 0.05)

    At d = 0 m:     P = 1.00 (100%)
    At d = 500 m:   P = 0.975 (97.5%)
    At d = 1000 m:  P = 0.95 (95%)

  Used exclusively for emergency vehicle ↔ RSU communication
  (higher priority, longer range, better reliability).


--- 13.3  Packet Delivery Determination ---

  Packet success is deterministic (not stochastic). A hash function
  determines delivery:

    hash_val = hash(source_id, dest_id, timestamp) mod 100
    delivered = (hash_val / 100) < P_success(d)

  This ensures reproducibility: the same source/dest/time always yields
  the same delivery outcome for a given distance.

  14. SECURITY CONFIGURATION
================================================================================

Source: v2v_communication/security.py, v2v_communication/key_management.py

When --security flag is enabled:

Cryptographic Primitives:
  ┌──────────────────────────┬────────────────────────────────────────────┐
  │ Component                │ Specification                              │
  ├──────────────────────────┼────────────────────────────────────────────┤
  │ Certificate Authority    │ RSA-4096 (CA key pair)                    │
  │ Entity keys (per RSU &   │ RSA-2048 (per-entity key pair)            │
  │   per vehicle)           │                                            │
  │ Public exponent          │ 65537                                      │
  │ Symmetric encryption     │ AES-256-GCM (32-byte key)                 │
  │ Digital signatures       │ RSA-PSS with SHA-256                       │
  │ Certificate validity     │ 365 days                                   │
  │ Serial number entropy    │ 16 bytes (128-bit random)                  │
  └──────────────────────────┴────────────────────────────────────────────┘

Security Initialization Flow (initialize_vanet_security):
  1. Create CertificateAuthority with RSA-4096 key pair
  2. Generate RSA-2048 key pairs for each of the 13 RSUs
  3. Generate RSA-2048 key pairs for each vehicle in the simulation
  4. CA issues X.509-style certificates to all entities
  5. RSUs register all vehicle public keys (from verified certificates)
  6. Vehicles register all RSU public keys (from verified certificates)
  7. Vehicles register peer vehicle public keys (for V2V)

Message Security (per V2V/V2I message):
  1. Generate random AES-256 session key (32 bytes)
  2. Encrypt payload with AES-256-GCM (authenticated encryption)
  3. Encrypt AES session key with recipient's RSA-2048 public key
  4. Sign message with sender's RSA-2048 private key
  5. Transmit: encrypted_data + encrypted_session_key + signature + nonce

Performance Impact:
  - RSA key generation at startup adds significant wall-clock time (~2×)
  - Per-message overhead: RSA encrypt + AES encrypt + RSA sign
  - Traffic simulation results are IDENTICAL (security is application-layer)
  - Only throughput (wall-clock based) and simulation time differ

================================================================================
  16. END-TO-END EXECUTION FLOW
================================================================================

This section describes exactly what happens during a single benchmark run
from start to finish.


--- 16.1  BENCHMARK ORCHESTRATION (run_benchmark.py) ---

  1. Parse arguments: seeds=30, seed-start=42, steps=1000, modes=[fixed,
     density, proximity]

  2. Generate seed list: [42, 43, 44, ..., 71]

  3. For each security setting (nosec, then sec):
       For each mode (fixed, density, proximity):
         For each seed (42 through 71):
           a. Check cache: benchmark_results/raw_metrics/{mode}_{sec}_seed{N}.json
              If exists → skip (load from cache)
           b. If not cached → spawn subprocess (Section 15.3)
           c. On success: read benchmark_metrics.json from output dir
           d. Cache the small JSON (~1 KB) to benchmark_results/raw_metrics/
           e. Delete the large output directory (~271 MB) to save disk space
           f. On failure/timeout: log error, continue to next run

  4. After all runs for a security setting complete:
     a. Aggregate metrics across 30 seeds per mode (np.mean, np.std)
     b. Build comparison table (14 metrics × 3 modes)
     c. Save CSV: benchmark_results/comparison_{no_security|security}.csv
     d. Save JSON: benchmark_results/aggregated_{no_security|security}.json

  5. Combine all 180 raw results → benchmark_results/all_raw_results.json


--- 16.2  SINGLE SIMULATION RUN (run_complete_integrated.py) ---

  For each spawned subprocess:

  1. INITIALIZATION
     a. Parse CLI arguments (mode, steps, seed, output, security, model, etc.)
     b. Set random seeds:
        - random.seed(seed)
        - numpy.random.seed(seed)
     c. If --security:
        - Create CertificateAuthority (RSA-4096)
        - Generate RSA-2048 key pairs for all 13 RSUs
        - Generate RSA-2048 key pairs for vehicles
        - Issue and exchange certificates
     d. Initialize AdaptiveTrafficController with mode, output_dir, etc.
     e. Connect to SUMO:
        - Launch `sumo -c simulation.sumocfg --seed {seed} --start`
        - Initialize intersection state (read traffic light programs)
        - Initialize WiMAX base stations at J2; J3
        - If --edge: Initialize 13 edge computing RSUs
     f. Initialize SUMONS3Bridge (network simulation layer)
     g. If --model and mode=proximity:
        - Load DQN model from ZIP file
        - Create ProximityHybridController (threshold=250m)

  2. MAIN SIMULATION LOOP (1000 steps)
     For step = 1 to 1000:
       a. traci.simulationStep()  — advance SUMO by 1 second
       b. Get all vehicle IDs, positions, speeds from SUMO
       c. Traffic light control:
          - Fixed: constant 30s green
          - Density: adaptive green based on _get_lane_density()
          - Proximity: check if emergency within 250m
            → Yes: DQN agent selects action
            → No: density-adaptive control
          - Emergency priority override (all modes): if emergency within
            150m, force green on its approach direction
       d. Network simulation:
          - V2V beacons (WiFi 802.11p) for nearby vehicle pairs
          - V2I messages (WiFi for regular, WiMAX for emergency)
          - If --security: encrypt/sign all messages
       e. Track metrics:
          - For each vehicle: accumulate wait time (if speed < 0.1 m/s)
          - For each vehicle: accumulate distance (speed × 1s)
          - Detect completed vehicles (disappeared from simulation)
          - Record queue lengths (halting vehicles per lane)
       f. If --edge: Update edge RSU vehicle registrations and services

  3. METRICS COMPUTATION (after loop ends)
     a. Compute per-run averages from accumulated data:
        - avg_wait_time = mean(wait times of completed vehicles)
        - avg_trip_speed = mean(distance/time for completed vehicles)
        - avg_queue_length = mean(queue per step)
        - total_completed_vehicles = count of completed
        - throughput = completed / wall-clock minutes
     b. Compute emergency vs normal vehicle subsets
     c. Retrieve network PDR from NS3 bridge (wifi_pdr, wimax_pdr)
     d. Write benchmark_metrics.json to output directory

  4. CLEANUP
     a. Close SUMO connection (traci.close())
     b. Process exits; run_benchmark.py reads the metrics JSON
     c. Large output files (~271 MB) are deleted; only ~1 KB cache kept


--- 16.3  DISK SPACE MANAGEMENT ---

  Each simulation run generates approximately 271 MB of output files
  (SUMO XML logs, trip info, edge computing logs, etc.). For 180 runs
  this would require ~48 GB. To manage this:

  - After each run, run_benchmark.py caches only the small benchmark
    metrics JSON (~1 KB) to benchmark_results/raw_metrics/
  - The full output directory is deleted via shutil.rmtree()
  - Total benchmark storage: ~180 KB (180 × ~1 KB cache files)
  - If a cached file exists, the run is skipped entirely (idempotent)

  This also enables re-running failed seeds without repeating successful ones.


--- 16.4  DATA QUALITY VALIDATION ---

  After all 180 runs completed, validation was performed:

  1. File count check: 180 JSON files in benchmark_results/raw_metrics/
     (60 per mode: 30 nosec + 30 sec)

  2. Mode correctness: Verified each JSON's "mode" field matches filename
     (caught a data quality issue where proximity_nosec files had mode=
     "density" due to model load failure under Python 3.11; fixed by
     re-running under Python 3.8)

  3. Step count: All files have steps = 1000 (999–1000)
     (caught an issue where seeds 42–44 had steps = 300 from an earlier
     quick test; deleted and re-run)

  4. Metric validity: No NaN or null values in any metric field

  5. Sample size: n = 30 for every (mode, security) group (confirmed
     in aggregated JSON files)
